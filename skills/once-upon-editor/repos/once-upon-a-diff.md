# once-upon-a-diff

This checkout's profile. To override it, put your own at `~/.once-upon/editor/once-upon-a-diff.md`; that file wins.

- Checkout: this repo's main checkout (the folder that holds `skills/`), GitHub owner from `git remote get-url origin`. Worktrees go in `../once-upon-a-diff-worktrees/<branch>`, next to the checkout. Briefs say to read `<checkout>/AGENTS.md` first.
- Stories (`repos.once-upon-a-diff.stories` in config.json is the yes/no; this is the how): every branch gets a local story the user reviews before deploy (since 11/6; this repo no longer skips review). Launch its storyteller with the critic, with `dispatch <card> --role storyteller --fan-out`: an open storyteller holds the card in Agent checks, the story waiting on the user shows in Ready for your review, and the approved one in Ready to ship. Nothing is pushed. `--fan-out` puts `Fan-out: yes` in its brief (the editor runs the chapter writers when 6 or more chapters need text: SKILL step 5b); a listener's Build story and an ad-hoc storyteller write alone.
- Heavy for `once-upon heavy`: the full `yarn test`, the whole-repo `yarn typecheck`, a whole-repo `yarn lint`, `yarn test:extension` and the pixel shots, and a whole-bridge `yarn workspace once-upon-a-diff test`, all on the main lock (`yarn test:extension` is a full browser run, not a single-spec one, so it stays there; `--lane browser` is not used in this repo). Light, run bare: targeted `node --test` files, `yarn format:check`, `yarn depcruise`, eslint on the changed files, `yarn workspace <pkg> typecheck` for each changed workspace, and a whole workspace's test other than the bridge's. An author runs the full suite, whole typecheck and lint only when its diff touches `packages/domain/`, `packages/server-libs/foundation/`, `configs/` or a `tsconfig*.json` at the repo root, and `yarn test:extension` and the pixel shots only for client changes; the deploy gate runs the full suite. (`scripts/deploy-local.sh` takes the lock through `once-upon deploy`, never also through `heavy`: nested, it would wait on itself.) A targeted `node --test test/<file>.test.ts` is light.
- Deploy (the editor runs it itself, never an author or an agent): `OU_MAIN=<checkout> ONCE_UPON_PATH="$PATH" fnm exec --using=24 once-upon deploy <name> scripts/deploy-local.sh --yes --batch main <sha>` (a cherry-pick of the branch's one commit that runs the gates, the full suite included, in the one `deploy` worktree; the live commit gets a new sha, which `backlog land` matches by the picked sha) is the default, because a fast-forward runs no gates. Fast-forward, `... scripts/deploy-local.sh --yes <branch>`, only when the user says so (the variable goes before the wrapper: `once-upon deploy` takes a program and its arguments, not shell syntax). If a batch cherry-pick conflicts, the diagnosis agent only reads the log and names the conflicting files (the next deploy run aborts the cherry-pick left in the deploy worktree itself), then a fresh fixer rebases onto main (the branch, the new base and the conflicting files in its brief), then deploy the batch again. Never restart the live bridge and never reload the extension. Briefs carry the targeted-gate line only when `repos.once-upon-a-diff.deploy_gate` is `true` in config.json: set it for this repo.
- Card order: `once-upon backlog list`, top first, skipping done, claimed and held cards.
