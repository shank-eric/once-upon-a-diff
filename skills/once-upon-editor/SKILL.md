# Editor: run a repo's build queue

Invoked as `/once-upon-editor <slots>` from inside a repo. Slots = the number in the args, default 3. You are the editor. Authors write the code, critics are fresh Opus reviewers, storytellers build a branch's story, and the user is the reader. If the user has a relay session (a voice session, say), it keeps the user, research and questions, and relays their decisions to you.

## First

1. Read the user's `~/.claude/CLAUDE.md`, this repo's AGENTS.md or CLAUDE.md and its project memory MEMORY.md if there is one, and the last ≈60 lines of the ledger file named by `board_ledger_file` in `<home>/config.json` (skip it when unset). `<home>` is `$ONCE_UPON_HOME` or `~/.once-upon`.
2. Read the user file `<home>/editor/_user.md` if it exists: it names the relay session, any extra notes or memory to read, and the default folder for critic reports. Then read this repo's profile: the first that exists of `<home>/editor/<current directory name>.md` and `repos/<current directory name>.md` next to this file. If neither exists, copy `repos/_template.md` to the user profile path, ask the user for the deploy command, claim command, card source and hand-over to fill it in, and stop.
3. Your sid8 is the first 8 characters of your session id (from your scratchpad path). Register yourself with the repo's editor command, which is its agent command with `editor` in place of `agent` (`start editor-<sid8> --slots <slots> --task "once-upon-editor, <slots> slots" --sid <sid8>`; `agent start --kind editor` is refused), check your slots with `slots editor-<sid8> --sid <sid8> --json`, and send the relay session, if there is one, one line of status.

## Dispatch only

You never edit repo code or run builds, tests or git work. Reading, checks, edits, deploys and cleanup go to named background agents (short kebab-case `name`, also in the description). Inline: the agent command's `start`, `state` and `finish`, SendMessage and one instant command.

- Authors: Sonnet, effort high. Critics: Opus, high. Storytellers: only when the repo profile calls for a story for the user. Pass effort on every Agent call.
- Small jobs use the lean agent types when the user has them (`subagent_type`): `lookup` for plan checks and read-only checks, `backlog-clerk` for card and ledger commands, `research` for web or file research. Without them, `general-purpose` at low effort. A per-role author, fixer or critic type, when one exists, replaces the general-purpose launch for that role. Fewer tools and a shorter prompt cost less on every turn.
- A brief gives the goal and why, the absolute checkout path, "read <checkout>/AGENTS.md first", the success check up front, what the agent must not do (no commit, push, PR, send or delete beyond what it names) and its notes file. Hand over file and line lists, not descriptions: the files to change or check, the `file:line` findings, the notes file's path and which section to read. Tell the agent to read line ranges (`offset`/`limit`, `grep -n`, `git diff <base>..HEAD -- <file>`), never a whole file it only needs part of. Agents report at most 3 short lines.
- Author briefs carry a soft cap: after about 100 tool calls without a passing success check, commit what passes, write what is done and what is left (`file:line`) to the notes file, set `state --state waiting` and hand back; the editor finishes the capped author (`finish <name> --state done --outcome "capped; notes hold the rest"`, with `--commit` if it committed) so no run stays open, then continues with a fresh author from that notes file.
- A fresh agent is the default for every follow-up on a branch (the build after a plan check, a fix round, a rebase). Resuming by SendMessage extends the author's whole context, which grows about 2k a turn and is billed again on every turn after it. SendMessage is only for a one-line answer to an agent that is still running or waiting and whose context is still small (about 100k or less), and never to start another round of work.
- Heavy runs take turns machine-wide. Every brief says: "Run every heavy command through the lock: `ONCE_UPON_PATH="$PATH" fnm exec --using=24 once-upon heavy <your name> <command>` (e.g. `... once-upon heavy <name> yarn test`; plain `once-upon heavy <your name> <command>` where the shell is on Node 24). Heavy means the full test suite, a browser run, a whole-repo typecheck or lint and deploy gates, as the repo profile lists them; a targeted single-file test is light and runs bare. The lock may make you wait for another agent's run, so start heavy commands with `run_in_background: true` and wait for the notice. Before your final report, wait for every background command you started to finish (or stop it), so nothing of yours is still running when you hand back." The deploy agent's brief says it too.
- Backlog clerk: if you need card adds, moves or edits beyond your own claims, check ListAgents for a running clerk and SendMessage it; if none is running, launch your own (`backlog-clerk`, Sonnet, effort low, `--kind helper`) and send it the backlog ops. Claims stay yours.
- Every brief carries the beat line `fnm exec --using=24 once-upon beat <name> <N>/<M> <step> "<few words>"` (plain `once-upon beat` where the shell is on Node 24; a failing beat means Node 24 was not found, so the agent tells you), the finish line `<agent command> finish <name> --state done|failed --outcome "<one line>"` (`<agent command>` is in the repo profile; `state <name> --state waiting|review --outcome "<question or story id>"` instead when it needs the user or is parked on their review; an author's or fixer's finish also adds `--commit <sha> --branch <b> --card <id>`, so its card marks itself landed (a fixer amends, so the card records the new tip), and other agents don't need those flags), and, when the user file names a relay session, the forwarding line it gives (what the agent forwards to the relay session by SendMessage, word for word, and when).

## Ledger and slots

Register each agent just before the Agent call, so its first beat finds its run, with the repo's agent command. A run on a card: `<agent command> start <name> --card <id> --role author|fixer|critic|storyteller --task "<task>" --sid <sid8> --model <m> --effort <e> --cwd <the agent's worktree>`; the card gives the repo and branch, so leave out `--repo`, `--branch` and `--lane`. A fix round or a rebase is a new run on the same card under its own name (`fix-<branch>`, `--role fixer`), started after the author's run is finished: a second open author on a card is refused, and a finished one is not. Re-claim the card for the fixer right after launching it (`--agent fix-<branch>`). Lookups, deploys and cleanup with no card: `start <name> --kind helper|research --task "<task>" --sid <sid8> --model <m> --effort <e> --repo <owner/name>`. It writes the ledger's `[running]` line, so type none. `state <name> --state waiting|review|plan|fixing --sid <sid8>` and `finish <name> --state done|failed|stopped --sid <sid8>` write the later ones; a critic finishes with `--findings N` (0 if none). If the Agent launch is refused or errors after `start`, run `finish <name> --state failed --sid <sid8>` at once. When an author renames or switches its branch, it runs `once-upon backlog branch <card> <new-branch>` so the card and its open runs follow (the board keeps the worktree and story); a storyteller of a PR with no card starts with `--role storyteller --pr N` (the PR's head branch is read through gh).

Count slots with the editor command's `slots editor-<sid8> --sid <sid8> --json` (`in_use`, `free`): it counts the authors on cards you claimed that are running, at the plan check or fixing, the same count the board shows. More than the slot count needs the user's go-ahead. A fixer or a build-after-plan holds a slot like any author (the count is per open author run, so the finished author holds none). Re-run it after every report.

## Loop

1. Take open cards in the repo profile's order, skipping done, claimed and held ones. Claim each with the repo's claim command.
2. Launch authors up to the slot count.
3. Plan-stop cards (new feature, shared contracts or schemas, auth, more than ≈a day): the author writes its plan to its notes file, posts beat 2 and stops. A lookup agent checks it against the code and brief and writes any corrections to the same notes file under a "Plan check" heading. Then finish the planner (`finish <planner> --state done --outcome "plan checked"`, no `--commit`) and, in the same step, start a fresh author `<planner>-build` (`--role author`, same card) and re-claim the card for it with the repo's claim command (the planner's finish ends its claim) whose brief is the notes file's path, "build from its plan and its Plan check corrections", and the usual rules and success check. Do not SendMessage the planner to build. A plan that departs from something the user decided goes to them (through the relay session, if there is one) before the build starts: keep the planner in `plan` state meanwhile and finish it only when the build starts.
4. Per branch: author builds (one commit) -> fresh Opus critic `review-<branch>` (read-only, `base..HEAD` plus the branch's intent, not your conclusions, never a code-review skill; findings with `file:line`, failure and confidence to `<reviews>/<date>-<branch>-agent-review.md`, where `<reviews>` is the folder the user file names, else the one the repo profile names, else `<home>/reviews`) -> you check each finding against the code -> a fresh fixer `fix-<branch>` fixes the clear bugs in one round (its brief: the branch and base, the checked findings as `file:line` with the failure, the findings to skip and why, the author's notes path for intent only, the success check; it amends the branch's one commit, never adds a second) -> deploy per the repo profile -> a cleanup agent removes the landed worktree and branch and moves that card's notes files (the author's `<branch>.notes.md`, the plan check's notes, any card-note scratch file) to the Trash, keeping any file an open card still points to. A rebase (a conflicting deploy) goes the same way: a fresh fixer with the branch, the new base and the conflicting files, amending the one commit.
5. Refill the moment a slot frees.
6. When an agent has reported and its run is finished but its task still says it is waiting on its own background work, stop the task (TaskStop). Before telling the user it is safe to clear or exit, check that no task of yours is still running or waiting.

## Relays

With a relay session, SendMessage it, one or two lines each, for only: a landed deploy (one line per deploy), anything needing the user, a plan that departs from their decisions, a failure. Nothing else. Never relay push approvals. With none, say these in your own window.

## Hard limits

No push, PR, message send or delete without the user's ask by name. Never run prod commands. Don't touch worktrees or agents that another session's ledger lines own. Report times in the user's time zone (`time_zone` in config.json).
