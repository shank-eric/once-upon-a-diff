# ADR-07: The agent board as a bridge page

Descriptive, of the code on main at 7fa8447 (11/4). The review inbox page this ADR first covered was removed in 1eb023f, and its jobs moved to the board. Since 11/5: the board's services are `orchestration/board/` in `packages/core`, the top tier (ADR-21), and the paths below say so; the backlog is `queues/backlog/`, the story lists `features/review/`, and the registry `records/agents/` (it was `services/ledger/`). The ledger fallback named below is gone (ledger trim, 7a9512f).

## Context

Stories pile up across repos and PRs, and Claude sessions and background agents run in many iTerm tabs. The reviewer needs one place for "what waits for me" and "where is each piece of work", and for the backlog of work not yet started. The bridge already serves pages and holds the stories.

## Decision

- **One more page served by the bridge**, `/board/`: a page shell plus a type-stripped script (`packages/web/public/board.ts`, over the regions in `public/board/`), with its own page key (ADR-02) and an optional cookie on a proxy name. It's opened from `once-upon board`, the options page, or Alt+Shift+B, and polls every 3 s while visible.
- **Cards by branch or PR, in columns** Backlog, Working, Agent checks, Waiting, Research, Ready for your review, Ready to ship, PR open, Back to you, Done, Idle and Error, laid out by repo (`packages/core/src/orchestration/board/columns.ts` has the rules, and `packages/core/src/orchestration/board/agent-home.ts` where a finished agent goes). Research holds a finished research agent that has no card to sit in and made nothing. A story is a card, so the board is also where PR and local stories wait for review. A local story you've approved at its head waits in Ready to ship until its commit is delivered.
- **Agents come from the registry.** A session registers each agent with `once-upon agent start|state|beat|finish` (`agents.jsonl`, ADR-04), with its kind (author, critic, helper, research, or editor for a session running a repo's queue), repo, branch, PR, card and lane, and the board places it by those fields, never by its task text. Since 11/5 the board reads only the registry: the ledger fallback (a ledger file read for agents with no registry events) went with the ledger trim (7a9512f), and the ledger and progress files are logs the registry writes (ADR-11).
- **Claims link a card to its agent.** `once-upon backlog claim <id> --agent <name>` is the only link between a Backlog card and an agent: a claimed card sits in Working with its agent on it, and the agent has no card of its own (`packages/core/src/queues/backlog/claims.ts`). A claim is for one run. A deploy marks the card done by the commit its agent's finish recorded (`backlog land`), never by a branch name.
- **A critic gate before Ready to ship.** A claimed card whose author has finished waits for a registered critic on it (`--kind critic`, `--card`): in Agent checks while none is registered, one runs or its last run failed, and while its findings wait for a fix round in Working (the author runs), Waiting (the author is at a question or a plan) or Agent checks (at its fixing gate, or before the round starts). The rules are `criticHold` in `packages/core/src/queues/backlog/claims.ts`, applied in `packages/core/src/orchestration/board/stages/backlog.ts`. A critic that finishes with no findings, or a fix round finished after the findings, lets the card go on.
- **Editors.** A session registered with `--kind editor` (it runs a repo's build queue) gets a strip above the columns while it is live: its lane, how many of its slots its authors hold, and each author launched under its session id, with where it stands (`stages/editors.ts`).
- **Other surfaces on the same page:** a Listeners lane (who listens for which repo, with Stop listening), a worktrees lane, a strip of blank sessions in Idle, usage meters in the header, and a voice side panel for the Larmor session.
- **It's built from** Claude Code's session registry, iTerm tab status, the agent registry (`agents.jsonl`), Larmor's voice files, status line files, listeners, build and fix requests, local and PR stories (`packages/core/src/features/review/story-lists.ts`), `git worktree list`, and GitHub (approvals, checks, threads, requested reviews). ADR-11 lists the outside sources.
- **Actions from the page:** focus a tab, type Build story, Start listening or Assign into a session, Stop listening, Open story, Mark reviewed, add, move and drop Backlog items, Start, Pause, Resume and Stop voice, phone mode, and worktree Clean up. The writes beyond the bridge's own files are in ADR-11.
- **The Backlog is ours.** Its items live in `backlog.jsonl`, an append-only event log (ADR-04), and can be added from the page or `once-upon backlog`. A started item rides on its work's card and is linked to its worktree, session and registered agent.
- **Snapshots are cached 2 s, and GitHub is never waited on.** The board reads what the GitHub watcher (`packages/core/src/features/review/github-watcher.ts`, the `AutoReview` class) already has and starts checks in the background, and a restart shows what GitHub last said (`github-answers.json`). The watcher is also what marks a PR story reviewed on its own (you reviewed after the story was built, or every file is Viewed) and what drops a merged one (`merged.json`).

## Consequences

- No new app or service: the board shares the bridge's process, port, auth and files. Typing into a session is the `Sessions` service (`packages/core/src/features/sessions/sessions.ts`), which asks the board for what it needs through a `SessionsFeed` interface and imports nothing from `Board`. The board's routes call `app.sessions`, but Start listening in the panel (`packages/server/src/routes/story.ts`) still goes through the one-line delegates `Board` keeps, so the panel's routes depend on the board object at run time.
- **The bridge has two jobs.** It's a story server (product-shaped, generic), and a personal dashboard built around one setup: iTerm2's `it2`, a Stop hook that sets tab status, an agent-ledger line format, Larmor, a status line script and `~/.claude` internals. Most of it is behind `board_*` settings, but it's in the same process, with its routes in `server` and its rules in the top tier of `core`.
- **The board is the biggest part of the bridge.** `packages/core/src/orchestration/board/` is about 3,470 source lines on 11/5 (3,250 on 11/4): `board.ts` (the actions and the cache, 640 lines) over `stages/` (what each source adds to the data, about 2,400 lines), and the board's test file (`packages/bridge/test/board.test.ts`, in the shell because it starts a bridge) is 6,530 lines. Sessions, worktrees, the backlog, the agent registry and the story lists are services of their own, in lower tiers, and voice is a file inside the board's folder (`voice.ts`). Column rules (`columns.ts`) encode review etiquette (whose turn it is), which will keep changing.
- The board page is a Preact tree that the poll feeds, and Preact's keyed diff keeps focus, scroll and half-typed text without being told to (ADR-14, ADR-16).
- The watcher's one GitHub check per PR costs a large GraphQL query per PR every 3 min while the board is open.
- Each poll walks the registry, `ps`, `it2` per session, the worktree list and the story list (the 2 s cache absorbs a second tab).

## Open questions

1. Is the board part of the product that goes to the Web Store, or the author's own tool that happens to live in the bridge? With a board this size, and Start listening depending on it, should it move to its own package or a plugin, so the bridge can ship without it? What would have to come out of `Board` first (the session registry and typing)?
2. ~~Should the ledger format be documented as an interface (or replaced by an API) rather than parsed by regex from a notes file?~~ Answered 11/3 and 11/4: agents register through `once-upon agent`, and the board no longer parses the ledger (ADR-11).
3. Should the board keep stories past 30 days for anything unreviewed?
